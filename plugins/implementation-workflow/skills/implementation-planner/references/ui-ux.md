# UI / UX

UI/UX は最上位価値。ただし「きれい」「すっきり」ではなく、ユーザーの理解、判断、操作、回復、継続利用を基準にレビューする。

この file を UI/UX の canonical rubric とする。executor / auditor / testing 側は、この基準を実装時・監査時・検証時の checklist に落とす。

## Core Model

- 初見ユーザー、日常利用ユーザー、一般知識ユーザーの視点を入れる。
- UI は特段指示がない限り日本語。
- 内部都合、実装用語、DB 項目、queue、model run、分類名、backend 処理名をそのまま露出しない。
- 画面ごとに「ユーザーは何を理解するか」「何を判断するか」「何を操作するか」「操作後に何が起きるか」を明示してから設計する。
- UI は state machine として見る。loading、skeleton、empty、error、partial success、success、disabled、permission、long-running progress を設計する。
- 自動化や AI は、入力負荷、言語化負荷、比較負荷、判断負荷、回復負荷を下げる場合に使う。AI があるだけでは UX 改善ではない。

Evidence priority:

- 最優先は、その product の実ユーザー、実ブラウザ、実データ、実業務フローで観察できる結果。
- 次に、既存 product / design system / 運用チームが反復利用して成果を確認してきた pattern。
- 外部資料を参照する場合は、UI/UX が高く評価されている実サービスを継続運営する product team の公開 design system / content guideline / interaction pattern を優先する。
- 一般化された UX research は仮説生成と review checklist に使う。現在の product で検証せずに正解扱いしない。
- 規格、政府サイト、platform guideline は、法令・契約・accessibility baseline・host platform 制約が必要な場合の guardrail として使う。良い UX の主根拠にはしない。
- NN/g などの heuristic は、状態の可視化、ユーザーの言葉、ユーザー制御、一貫性、エラー予防、回復可能性を見落とさないための補助線として使う。

## Layout And Responsiveness

- モバイル / デスクトップ両対応を必須にする。
- responsive CSS だけを画面サイズ対応と見なさない。mobile で潰れないことと同じ重さで、desktop で視線移動、スクロール、マウス移動が過剰にならないことを設計要件にする。
- 広い画面では余白を増やすのではなく、関連する情報、比較対象、操作を近接させるために横幅を使う。
- breakpoints は見た目の切替ではなく、読み順、比較、確認、操作、ナビゲーションが各画面幅で成立するかを基準に決める。
- 情報量は多すぎても少なすぎても UX を損なう。初回理解に必要な情報は隠さず、低頻度・高度・例外的な情報は段階的に開示する。

## Action Placement And Semantics

- 主要アクションは、画面の下端や別領域に置けばよいわけではない。ユーザーが判断材料を読んだ直後に届く場所へ置く。
- 「読む、理解する、判断する」が連続する画面では、CTA をレポート本文や判断材料から分離したフッターだけに置かない。
- 判断材料、推奨理由、リスク、次の操作を近接させる。ユーザーが内容を読んだ後に別領域へ探しに行く導線は P1 候補として扱う。
- 1 つの意図には 1 つの導線を原則にする。同じ意味の操作を複数ラベルで出さない。
- 同じラベルのボタンを複数箇所に置く場合は、なぜ複数必要か、どちらを押すべきか、押した後の結果が同じかを明確にする。説明できない重複は削除する。
- 主導線、補助導線、保留、破壊的操作の優先度を、位置、見た目、文言で分かるようにする。
- 判断系 UI では、ボタンそのものを説明カード化しすぎない。説明は近接テキスト、補助文、比較表、詳細 disclosure に逃がし、ボタンは押しやすく比較しやすい形を保つ。

## Result-Centered Copy

- UI の言葉は、システムが何を保存、分類、処理するかではなく、ユーザーが何を判断していて、その結果なにが起きるのかを説明する。
- 操作コピーでは、誰が操作しているか、何に対する操作か、操作後に状態がどう変わるか、誰に見えるか、通知されるか、後から戻せるかを必要に応じて明確にする。
- 「保存される理由」「判断理由を入力」「処理対象外に分類」のような内部都合の言葉を主役にしない。「見送り」「保留」「一覧から外す」「相手には通知されません」「あとで見直せます」のように、ユーザーに起きる結果を主語にする。
- ユーザー向け UI 文言は、ユーザーに行動を指示する言い方ではなく、判断材料を中立に提示する言い方にする。
- 特に、作り手都合の誘導に見える `次に〜`、`〜したい`、`1問`、`深掘り`、`やること`、`できること` は避ける。確認、判断、流れ、復旧の対象が分かる名詞句に置き換える。
- 推奨する表現は `確認ポイント`、`確認が必要な〜`、`判断が必要な〜`、`この後の流れ`、`復旧方法`。ただし、画面の実態に合わない定型置換はしない。
- 説明量は risk に応じて調整する。高リスク、初回、不可逆、通知、共有、削除、個人情報や機密情報の開示では厚く説明し、繰り返し行う低リスク操作では短くする。
- 常時表示する説明は、誤解されると危険な一点に絞る。例: 通知が送信されるか、相手に見えるか、ワークスペース内だけか、あとで変更できるか。
- システムの都合でユーザーに作文させない。目的達成に必須でない入力は任意にし、「理由」ではなく「メモ」「補足」「相手に伝えたいこと」などユーザーの目的に沿う名前にする。

Before / After 例（内部都合・行動指示 → 結果中心・中立提示）:

- Bad: `ステータスを「処理対象外」に更新しました` / Good: `この件を一覧から外しました。相手には通知されません。あとで「対応済み」から戻せます。`
- Bad: ボタン `却下` のみ / Good: ボタン `見送る`＋補助文 `候補から外します。相手には通知されません。`
- Bad: 必須入力 `却下理由を入力してください` / Good: 任意入力 `メモ（チーム内だけに残ります・任意）`
- Bad: トースト `保存しました` / Good: トースト `下書きを保存しました。公開していません。`
- Bad: 確認 `本当に削除しますか？` のみ / Good: `この請求書を削除します。復元できません。`＋実行後に `削除しました（30秒間は取り消せます）`
- Bad: `次に確認したい1問` / Good: `確認ポイント`
- Bad: `次に見る募集` / Good: `確認が必要な募集`
- Bad: `次に判断する候補者` / Good: `判断が必要な候補者`
- Bad: `次にやること` / Good: `この後の流れ`
- Bad: `次にできること` / Good: `復旧方法`

## State, Feedback, And Recovery

- ユーザーが操作したら、即時 feedback を返す。保存中、処理中、完了、失敗、部分成功、再試行可否を曖昧にしない。
- spinner だけで状態を表現しない。待つべきか、他の操作ができるか、どの程度待つか、失敗したらどうするかを必要に応じて示す。
- エラーは、何が起きたか、どこを直すか、次に何をすればよいかを書く。可能なら入力を保持し、該当箇所へ誘導する。
- undo、cancel、back、escape、下書き保存、復元、履歴を設計要件として見る。不可逆操作だけでなく、長い入力、AI 生成、承認、送信でも戻れるかを確認する。
- 破壊的または不可逆な操作では、結果を具体的に書き、安全な出口を明示する。取り消せる場合は確認ダイアログより undo / restore を優先候補にする。

## Work Progress After Actions

- 操作後は、システム状態が変わるだけでなく、ユーザーの仕事が前に進んだことが画面上で分かる必要がある。
- 成功時は「保存しました」「更新しました」だけで終えない。対象がキューから外れた、次の対象に進んだ、完了状態になった、親一覧へ戻った、通知/共有/送信された、通知されていない、後から見直せる場所に移った、undo できる、のいずれかを明確にする。
- 一覧、審査、承認、判断、レビューなどのキュー型 UI では、操作後に対象がキューから外れるか、次の対象へ進むことを基本にする。
- ボタンを押しても同じ画面に残るだけ、色や小さな badge だけが変わるだけ、状態名だけが変わるだけの操作は疑う。業務上の意味が画面に出ていなければ UX 上は成功していない。
- 実質的に何も変わらない操作を選択肢として出さない。特に「保留」は、一覧上の扱い、通知、見つけやすさ、期限、リマインド、pin、メモなどの価値がなければ未操作のまま残す方がよい。
- 状態名は内部分類ではなく次アクションを示す。例: `処理済み` より `次の対応待ち`、`保留` より `あとで見る`、`ステータス更新済み` より `承認待ちから外れた`。

## Component And Copy Audit

- 既存 design system を優先する。未確定または greenfield の技術選定は `default-stack.md` 側で扱い、UI/UX rubric ではユーザー価値と操作品質に集中する。
- すべての component、label、button、heading、helper text、badge、icon、chart、empty message、toast、tooltip について「ユーザーにとって何の役に立つか」を確認する。
- なくしてもユーザーの理解、判断、操作、安心、進捗把握、エラー回復に影響がない要素は削除する。
- 意味がある要素でも、初見ユーザーが理解できず、行動や判断に役立たない表現なら書き換える。
- ユーザーが受け取ってもプラスにならない説明、装飾、重複情報、内部事情、曖昧な励まし、機能説明のためだけの文言は削除する。
- 情報を削りすぎて、次に何をすればよいか、現在どういう状態か、何が起きたか、どう回復すればよいかが分からない状態にしない。
- アイコン、グラフ、表、Mermaid、図表は、理解、比較、操作、状態把握、進捗把握に効く場合に使う。装飾だけで追加しない。

## Forms And Input

- 入力欄はユーザーの目的達成に必要なものだけにする。構造化データを集めたい都合を、ユーザーの作文負荷として押し付けない。
- 必須入力は、本当にその場の目的達成に不可欠なものだけにする。任意なら label に明記する。
- validation は失敗させるためではなく、成功させるために設計する。許容できる表記揺れは正規化し、false negative を減らす。
- エラー後も入力を失わせない。どの field をどう直せばよいか、ユーザーの言葉で書く。
- 同じ情報を何度も入力させない。再入力が必要な場合は理由を説明し、可能なら既知情報を再利用する。

## Accessibility And Interaction

- keyboard 操作、focus、label、role、contrast、target size、form error を確認する。
- pointer 前提の hover-only UI にしない。touch、keyboard、screen reader、拡大表示で成立するかを見る。
- focus は見えるようにする。モーダル、drawer、menu、toast、validation error は focus 移動と戻り先を設計する。
- target size と余白は、誤操作と手の移動の両方を考える。小さすぎる操作、近すぎる破壊的操作を避ける。

## Verification

- Web UI はハッピーパスを実ブラウザで操作する。
- 画面上の主要 component と文言を一つずつ見て、存在理由、理解可能性、ユーザー価値、削除可否を確認する。
- screenshot で desktop / mobile、長い日本語、狭いコンテナを確認する。
- 不自然な改行、単語分断、助詞だけの行、句読点だけの行、文字切れ、重なり、ボタン内テキストの窮屈さを見る。
- 判断材料と主要アクションが近いか、読了後に自然な位置へ CTA があるかを見る。
- UI 文言が `次に〜`、`〜したい`、`1問`、`深掘り`、`やること`、`できること` でユーザーの行動を誘導していないかを見る。必要なら `確認ポイント`、`確認が必要な〜`、`判断が必要な〜`、`この後の流れ`、`復旧方法` などの中立表現へ直す。
- 操作後に対象、状態、次アクションのどれが変わって見えるかを見る。キュー型 UI では、対象がキューから外れるか次の対象へ進むかを確認する。
- 「保留」など、押しても業務上何も進まない操作が選択肢に出ていないかを見る。
- desktop では、余白が広がるだけで関連情報と操作が離れていないか、視線移動とマウス移動が過剰でないかを見る。
- mobile では、主要 CTA が内容から遠すぎないか、長い説明ボタンで比較やタップがしづらくなっていないかを見る。
- ユーザーが何を決めているか、操作後に何が変わるか、誰に見えるか、通知されるか、戻せるかが必要十分に分かるかを見る。
- 内部状態、保存先、分類名、バックエンド処理、データ再利用、必須理由入力が UI copy の主役になっていないかを見る。
- 10 回目の操作でも説明がノイズにならないか、初回や高リスク操作で説明が不足していないかを見る。
- URL と画面状態を合わせる。browser back、reload、direct URL、URL share を確認する。
