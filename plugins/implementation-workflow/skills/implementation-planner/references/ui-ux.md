# UI / UX

UI/UX は最上位価値。「きれい」「すっきり」ではなく、ユーザーの理解、判断、操作、回復、継続利用を基準にレビューする。

この file が UI/UX の canonical rubric。executor / auditor / testing 側は、この基準を実装・監査・検証の checklist に落とす。

## Core Model

- 初見ユーザー、日常利用ユーザー、一般知識ユーザーの視点を入れる。
- UI は特段指示がない限り日本語。
- 内部都合、実装用語、DB 項目、queue、model run、分類名、backend 処理名をそのまま露出しない。
- 画面ごとに「何を理解するか」「何を判断するか」「何を操作するか」「操作後に何が起きるか」を明示してから設計する。
- UI を state machine として扱い、loading、skeleton、empty、error、partial success、success、disabled、permission、long-running progress を設計する。
- 自動化や AI は、入力、言語化、比較、判断、回復の負荷を下げる場合に使う。AI があるだけでは UX 改善ではない。

Evidence priority:

- 最優先は、その product の実ユーザー、実ブラウザ、実データ、実業務フローで観察できる結果。
- 次に、既存 product / design system / 運用チームが反復利用して成果を確認してきた pattern。
- 外部資料は、UI/UX が高く評価される実サービスを継続運営する product team の公開 design system / content guideline / interaction pattern を優先する。
- 一般化された UX research は仮説生成と review checklist に使う。現在の product で検証せずに正解扱いしない。
- 規格、政府サイト、platform guideline は、法令・契約・accessibility baseline・host platform 制約の guardrail として使う。良い UX の主根拠にはしない。
- NN/g などの heuristic は、状態の可視化、ユーザーの言葉、ユーザー制御、一貫性、エラー予防、回復可能性の見落とし防止に使う。

## URL And Navigation State

- ユーザーがページ、タブ、詳細画面、管理画面の対象、検索結果、絞り込み結果、workflow step と認識する状態は URL に載せる。local component state だけで画面を切り替えない。
- local state に閉じてよいのは、hover、tooltip、開閉中の一時 menu、未送信の入力途中、確認 dialog など、共有・復帰・戻る操作の対象にならない一時状態だけ。
- 一覧から詳細、管理対象の選択、設定カテゴリ、検索・sort・pagination、step 進行の導線は、reload、direct URL、URL share、browser back / forward で予想通り復帰できるようにする。
- 認証、権限、onboarding、tenant selection などの gate は、ユーザーが開こうとした URL を保持する。権限不足や未設定状態を、無関係な default 画面への強制 redirect で隠さない。
- redirect は現在地を失わせない場合だけ使う。失敗、権限不足、対象なし、設定不足は、その route 上で回復方法や戻り先を示す。
- reload、direct URL、browser back / forward、login 後復帰で対象喪失、誤った対象への操作、入力消失が起きる設計は P0/P1 にする。今回変更する route / query / work state に残っていれば完了扱いしない。
- 「画面は変わったのに URL が変わらない」「戻ると想定外の場所へ行く」「直接開くと同じ状態にならない」は P1 UX finding 候補。無関係な既存 route の問題は backlog 化し、accepted scope を自動的に広げない。

## Layout And Responsiveness

- モバイル / デスクトップ両対応を必須にする。
- responsive CSS だけで画面サイズ対応とみなさない。mobile で潰れないことと同じ重さで、desktop で視線移動、スクロール、マウス移動が過剰にならないことを要件にする。
- 広い画面の横幅は余白ではなく、関連情報、比較対象、操作を近接させるために使う。
- breakpoints は、読み順、比較、確認、操作、ナビゲーションが各画面幅で成立するかで決める。
- 初回理解に必要な情報は隠さず、低頻度・高度・例外的な情報は段階的に開示する。

## Action Placement And Semantics

- 主要アクションは、ユーザーが判断材料を読んだ直後に届く場所へ置く。
- 「読む、理解する、判断する」が連続する画面では、CTA を本文や判断材料から離れたフッターだけに置かない。
- 判断材料、推奨理由、リスク、次の操作を近接させる。読んだ後に別領域へ操作を探しに行く導線は P1 候補。
- 1 つの意図には 1 つの導線を原則にする。同じ意味の操作を複数ラベルで出さない。
- 同じラベルのボタンを複数箇所に置くなら、なぜ必要か、どちらを押すべきか、結果が同じかを明確にする。説明できない重複は削除する。
- 主導線、補助導線、保留、破壊的操作の優先度を、位置、見た目、文言で区別する。
- 判断系 UI ではボタンを説明カード化しすぎない。説明は近接テキスト、補助文、比較表、詳細 disclosure に置き、ボタンは押しやすく比較しやすく保つ。

## Result-Centered Copy

- UI の言葉は、システムが何を保存・分類・処理するかではなく、ユーザーが何を判断していて、その結果なにが起きるかを説明する。
- 操作コピーでは必要に応じて、誰が、何に対して操作し、操作後に状態がどう変わり、誰に見え、通知されるか、後から戻せるかを明確にする。
- 「保存される理由」「判断理由を入力」「処理対象外に分類」のような内部都合の言葉を主役にしない。「見送り」「保留」「一覧から外す」「相手には通知されません」「あとで見直せます」のように、ユーザーに起きる結果を主語にする。
- ユーザー向け文言は、行動を指示せず判断材料を中立に提示する。作り手都合の誘導に見える動詞・勧誘表現を避け、確認・判断・流れ・復旧の対象が分かる名詞句にする。具体例は下の Before / After。定型置換はしない。
- 説明量は risk に応じて変える。高リスク、初回、不可逆、通知、共有、削除、個人情報や機密情報の開示では厚く、繰り返す低リスク操作では短くする。
- 常時表示する説明は、誤解されると危険な一点に絞る。例: 通知が送信されるか、相手に見えるか、ワークスペース内だけか、あとで変更できるか。
- システムの都合でユーザーに作文させない。目的達成に必須でない入力は任意にし、「理由」ではなく「メモ」「補足」「相手に伝えたいこと」などユーザーの目的に沿う名前にする。

Before / After 例（内部都合・行動指示 → 結果中心・中立提示）:

- Bad: `ステータスを「処理対象外」に更新しました` / Good: `この件を一覧から外しました。相手には通知されません。あとで「対応済み」から戻せます。`
- Bad: ボタン `却下` のみ / Good: ボタン `見送る`＋補助文 `候補から外します。相手には通知されません。`
- Bad: 必須入力 `却下理由を入力してください` / Good: 任意入力 `メモ（チーム内だけに残ります・任意）`
- Bad: トースト `保存しました` / Good: トースト `下書きを保存しました。公開していません。`
- Bad: 確認 `本当に削除しますか？` のみ / Good: `この請求書を削除します。復元できません。`＋実行後に `削除しました（30秒間は取り消せます）`
- Bad: `次に確認したい1問` / Good: `確認ポイント`
- Bad: `次に見る募集` / Good: `確認が必要な募集`
- Bad: `次に判断する候補者` / Good: `判断が必要な候補者`
- Bad: `次にやること` / Good: `この後の流れ`
- Bad: `次にできること` / Good: `復旧方法`
- Bad: `候補者を深掘りする` / Good: `職務経歴の詳細`

## State, Feedback, And Recovery

- 操作には即時 feedback を返す。保存中、処理中、完了、失敗、部分成功、再試行可否を曖昧にしない。
- spinner だけで状態を表さない。必要に応じて、待つべきか、他の操作ができるか、どの程度待つか、失敗したらどうするかを示す。
- エラーには、何が起きたか、どこを直すか、次に何をすればよいかを書く。可能なら入力を保持し、該当箇所へ誘導する。
- undo、cancel、back、escape、下書き保存、復元、履歴を設計要件にする。不可逆操作だけでなく、長い入力、AI 生成、承認、送信でも戻れるかを確認する。
- 破壊的・不可逆な操作では結果を具体的に書き、安全な出口を示す。取り消せる場合は確認ダイアログより undo / restore を優先候補にする。

## Work Progress After Actions

- 操作後は、システム状態だけでなく、ユーザーの仕事が前に進んだことを画面上で分かるようにする。
- 成功時は「保存しました」「更新しました」だけで終えない。対象がキューから外れた、次の対象に進んだ、完了状態になった、親一覧へ戻った、通知/共有/送信された、通知されていない、後から見直せる場所に移った、undo できる、のいずれかを明確にする。
- 一覧、審査、承認、判断、レビューなどのキュー型 UI では、操作後に対象がキューから外れるか次の対象へ進むことを基本にする。
- 押しても同じ画面に残るだけ、色や小さな badge や状態名だけが変わる操作は疑う。業務上の意味が画面に出ていなければ UX 上は成功していない。
- 実質的に何も変わらない操作を選択肢に出さない。特に「保留」は、一覧上の扱い、通知、見つけやすさ、期限、リマインド、pin、メモなどの価値がなければ未操作のままにする。
- 状態名は内部分類ではなく次アクションを示す。例: `処理済み` より `次の対応待ち`、`保留` より `あとで見る`、`ステータス更新済み` より `承認待ちから外れた`。

## Component And Copy Audit

- 既存 design system を優先する。未確定または greenfield の技術選定は `default-stack.md` で扱い、この rubric はユーザー価値と操作品質に集中する。
- すべての component、label、button、heading、helper text、badge、icon、chart、empty message、toast、tooltip について、ユーザーにとって何の役に立つかを確認する。
- なくしても理解、判断、操作、安心、進捗把握、エラー回復に影響しない要素は削除する。
- 意味がある要素でも、初見ユーザーが理解できず行動や判断に役立たない表現は書き換える。
- プラスにならない説明、装飾、重複情報、内部事情、曖昧な励まし、機能説明のためだけの文言は削除する。
- 削りすぎて、次に何をするか、現在の状態、何が起きたか、どう回復するかが分からない状態にしない。
- アイコン、グラフ、表、Mermaid、図表は、理解、比較、操作、状態把握、進捗把握に効く場合だけ使う。

## Forms And Input

- 入力欄はユーザーの目的達成に必要なものだけにする。構造化データを集めたい都合を作文負荷として押し付けない。
- 必須入力は、その場の目的達成に不可欠なものだけにする。任意なら label に明記する。
- validation は成功させるために設計する。許容できる表記揺れは正規化し、false negative を減らす。
- エラー後も入力を失わせない。どの field をどう直すかをユーザーの言葉で書く。
- 同じ情報を何度も入力させない。再入力が必要なら理由を説明し、可能なら既知情報を再利用する。

## Verification

- level、browser 確認、screenshot、viewport の選び方は executor `testing-verification.md` に従う。
- 変更した component と文言について、存在理由、理解可能性、ユーザー価値、削除可否を確認する。画面全体の棚卸しは UI audit または redesign scope の場合だけ行う。
- 単語分断、助詞だけの行、句読点だけの行を見る。
- 変更箇所を上の各節で照合する:
  - Action Placement: 判断材料の近く、読了後の自然な位置に CTA があるか。
  - Result-Centered Copy: 文言が行動を誘導していないか（Before / After 参照）。何を決めているか、何が変わるか、誰に見えるか、通知されるか、戻せるかが必要十分に分かるか。内部状態、保存先、分類名、バックエンド処理、データ再利用、必須理由入力が主役になっていないか。10 回目の操作でノイズにならず、初回や高リスク操作で不足しないか。
  - Work Progress After Actions: 操作後に対象、状態、次アクションのどれが変わって見えるか。キュー型 UI では対象がキューから外れるか次へ進むか。押しても業務上何も進まない「保留」などが出ていないか。
  - Layout: desktop で関連情報と操作が離れず、視線移動とマウス移動が過剰でないか。mobile で主要 CTA が内容から遠すぎず、長い説明ボタンで比較やタップがしづらくないか。
- route / query、navigation、work state を変更する場合は URL と画面状態を合わせる。対象喪失、誤対象、入力消失は P0/P1 gate とする。
