# 依存更新の判断基準

リポジトリの設定（`.claude/repo-patrol.md` の「判断基準」）が別の文書を指していれば、そちらを優先する。この文書は、指定がないときの既定。

## 種類ごとの扱い

| 種類 | 扱い |
|---|---|
| npm 系以外（GitHub Actions・cargo・docker など） | 取り込まない。CI の状態を添えて報告し、人がそのままマージする |
| npm 系の patch / minor | 取り込む。公開から 7 日未満なら、7 日を満たすいちばん新しい版にする。それもなければ今回は見送る |
| npm 系のメジャー | 取り込まない。理由（移行が必要か、peer 依存の都合か）を 1 回だけコメントし、見送り中として報告する |
| セキュリティ（アラート・audit・本文に GHSA / CVE） | 修正版以上で 7 日を満たす最小の版にする。メジャー更新が必要、または 7 日を満たす修正版がなければ取り込まず、要判断としてメンションする |
| グループ PR（複数の依存をまとめたもの） | 中身を 1 つずつ上の基準で判断する。PR の lockfile はそのまま使わない（範囲内の最新化が混ざることがある） |
| 設定の見送り表にあるもの | 見直す条件を満たしていなければ、見送り中として報告するだけ |

## 公開日と中身の確かめ方

- 公開日: `npm view <name> time --json` で各版の公開時刻を見る。境界ちょうどの版は避ける
- インストールスクリプト: `npm view <name>@<version> scripts --json` に `preinstall` / `install` / `postinstall` があれば、取り込まずに要判断にする
- 公開者: 久しぶりのリリースや公開者が変わった版は、`npm view <name>@<version> _npmUser maintainers --json` を見て、変わっていれば要判断にする

## lockfile への適用

依存のコードを動かす前に lockfile の中身を確かめるため、まず lockfile だけを更新する。

| パッケージマネージャー | 方法 |
|---|---|
| pnpm | package.json の版を書き換え、`pnpm install --lockfile-only --ignore-scripts` |
| npm | package.json の版を書き換え、該当ディレクトリで `npm install --package-lock-only --ignore-scripts` |
| yarn | 要判断（巡回の対象外） |

- 指定した版を範囲の最小値にする（例: `^1.2.3` の 1.2.3）。範囲だけを書き換えると、範囲内の最新（7 日未満を含む）に解決されることがある
- 書き換えてよいのは、`^1.2.3`・`~1.2.3`・`1.2.3`（npm alias なら同じ alias 先）の形の値の版だけ。記号は変えない。`workspace:`・範囲指定・git などの値は変えない。prerelease（`-rc.1` など）にはしない
- overrides は既存のキーの版を上げるだけにする。推移依存だけが脆弱で overrides を足す必要があるときは要判断にする
- 適用したら、lockfile の差分で目的の依存以外の版が動いていないかを見る。動いていて戻せなければ要判断にする
- 最後に `check-diff.mjs` を通す（push の前に guard も通す）。依存や overrides の追加・削除、版下げ、記号や alias 先の変更、scripts などの変更、レジストリ以外からの解決、同じ版の integrity の変更を拒否する

## よくある落とし穴

- 同じ依存を複数の package.json で宣言している monorepo では、すべて同じ版にそろえる
- 同じ advisory が別の lockfile（サブディレクトリの独立したプロジェクトなど）にもあることがある。設定の「lockfile の場所」をすべて見る
- biome を上げたら `biome.json` の `$schema` も同じ版にする（設定で `biome.json` を追加パスとして許している場合だけ。許していなければ要判断）
- 対で上げる依存（同じスコープの関連パッケージなど）は、片方だけ上げない
